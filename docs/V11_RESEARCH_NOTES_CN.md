## 2. JSON字段必须区分

`action_chunks.jsonl`每行包含50×14预测目标，以及request_id、observed_sent_action_count、apply_sent_action_count、received_at_monotonic_ns。14维排列为L6,gL,R6,gR。

`actions_rad_m`记录模型空间转换后的绝对关节目标与夹爪开口。`actions_deg_mm`记录命令单位目标。逐项检查发现，两字段**不只有单位差异**：

- 十二个关节严格满足rad↔degree转换。
- 夹爪预测开口小于20 mm时变为0。
- 开口超过70 mm时封顶为70 mm。
- 上述映射在全部chunk的所有行上验证通过。

因此0.005 m与0.015 m两个不同的预测夹爪值，可能对应完全相同的实际闭合指令。重复判断应在控制接口处理后的动作语义中进行，不能对原始14维输出直接做距离比较。

`executed_ticks.jsonl`约60 Hz，全部向量采用度/毫米：

| 字段 | 作用 |
|---|---|
| requested | 当前tick请求的目标，可能已经过队列、接续或平滑处理 |
| sent | 实际下发的目标，已包含控制接口限幅及量化影响 |
| measured | 记录到的机械臂反馈；不能当成当前刚发命令的即时结果 |
| source=provider | 约30 Hz的策略目标步 |
| source=interpolation | 策略步之间的插值命令，也是实际施加的控制输入 |
| source=transition | 任务切换/初始过渡；不能混进折叠动作重复历史 |
| request_id、chunk_step_index | 关联对应chunk及原始行 |
| sent_policy_action_count | 策略步计数，与含插值/过渡的sent_action_count不同 |

在全部provider行验证：

```
chunk_step_index = sent_policy_action_count - 1 - observed_sent_action_count
```

新chunk开始使用时，已过期前缀的中位数为11个策略步；在名义30 Hz下约0.37秒。这是策略步年龄，不是精确的模型推理耗时，因为日志没有观测采集时间。

每段预测50步，但实际使用的provider行只占全部预测行的45.6%–47.8%。`check_20260920_222119`中的request_id=124收到后没有实际执行。约47%–49%的provider请求关节值与原始chunk对应行存在可测差异；因此原始预测行与实际requested不能互换。数据可确认存在下发前目标处理，但本地未找到日志产生端源码，不能据此声称完整复原了具体平滑算法。

应使用以下链条，而不是拼接整个chunk：

```
原始预测 → 单位/夹爪处理 → 丢弃过期前缀/目标接续
        → requested → 限幅/量化 → sent → 机械臂响应 → measured
```

## 3. 这批数据真正暴露了什么

### 3.1 限幅非常常见，且限幅损失较大

| 轨迹 | 配置关节步长上限 | policy tick限幅比例 | 最大关节裁剪量 |
|---|---:|---:|---:|
| EP0 | 7.5°/tick | 69.76% | 33.65° |
| EP1 | 10°/tick | 39.53% | 26.47° |
| EP2 | 10°/tick | 28.21% | 25.15° |
| EP3 | 10°/tick | 58.27% | 51.83° |

比例与原limit_check_summary逐项重新计算一致。过渡tick单独排除。这里的配置上限是控制软件参数，并非已核实的机械关节位置极限、速度上限或碰撞距离。

因果诊断实现了`max_j |requested_j-sent_j| / configured_step_limit`和过去0.5秒内的限幅tick比例。EP0约1.05秒就出现“被裁掉的量超过一个配置步长”的事件，明显早于重复报警；这提示可以更早观察到执行失配，**并不证明1.05秒就是任务故障起点**。正常快速运动也可能限幅，必须通过正常执行分布校准。

### 3.2 单个chunk速度/加速度并不异常大

从2246条正常训练轨迹抽取287488个样本，计算十二关节观测速度和加速度的99.9%分位包络。对新chunk只检查过期前缀之后的未来行，使用名义30 Hz时间间隔。

四组chunk的最大速度/正常包络比依次约0.933、0.978、0.751、0.821；最大加速度比约0.609、0.543、0.493、0.616。即这些单chunk内部路径均未超过该宽松包络。

因此，把“动作很快”作为主要报警依据很可能仍漏掉这些案例。包络来自正常观测运动，不等于硬件极限，也没有被当作命令OOD的正式阈值。跨chunk接续、从当前真实姿态出发是否可实现，比单chunk内部光滑性更关键。

### 3.3 相邻规划对同一未来时刻有较大分歧

按照全局policy步对齐新旧chunk，仅比较当前尚未执行的共同未来区间。先丢弃旧于apply_sent_action_count的行，再比较对应的十二个关节目标。

新旧目标RMS差异的中位数分别约16.10°、13.91°、17.10°、24.73°，最大值约34.44°、29.01°、26.65°、31.60°。这不是把两个chunk都从第0行开始比较得到的假差异。

重规划本来允许修改目标，不能将规划分歧单独硬判异常。但“重规划频繁改变方向→控制接口大量裁剪→本体与物体没有取得对应进展”是一条比纯state周期性更早出现的因果线索。

### 3.4 反馈必须与过去真正下发的命令比较

当前实现提供一个明确标注为诊断的100 ms历史命令对照：取当前时间之前至少100 ms的最后一个sent，与当前measured比较。四组十二关节RMS差异P50约0.90–1.23°，P95约2.09–3.17°。

100 ms只是展示设置，没有用失败日志拟合成“正常伺服时延”。现有数据没有精确的measured读取时间或控制生效时间；如果直接比较`measured_t`与`sent_t`，会将正常伺服延迟误判成跟踪失败。工程接入需要记录状态读取时间、命令发送时间，并用正常真实执行数据辨识时延和响应模型。

## 4. 怎样嵌入模型并维持三个最终判据

### 第一项：将静态投影距离扩展为动作条件响应距离

在关节空间就能先做，不要求URDF。可辨识的基线为：

```
qdot_pred = f(q_t, qdot_t, sent_t及最近命令历史, dt)
q_pred(t+h) = q_t + 积分预测速度
```

应使用实际sent驱动反馈预测；使用requested与约束投影的差异描述计划可实现性；使用共同未来区间的新旧计划差异描述接续。所有参考分布拟合正常真实命令，不能把这四条失败轨迹自动视为正常。

可以把这些内部量压缩为一个条件距离：

```
execution_feature = [限幅损失, 延迟对齐后的响应残差, 计划接续残差]
D_action = 正常条件分布中的标准化距离
```

然后将D_action与现有D_projection在各自正常尾部尺度上合并，再重新建立第一项的正常参考和最终校准。对外仍只有“动作条件距离、重复、LINe”三项，避免增加一排互相冲突的硬阈值。

只有硬件或控制接口确实提供了关节上下界、速度和加速度上限，才能把它们加入可行域投影。当前7.5°/10°每tick不能直接推断成真实物理速度上限；URDF可以后续补充自碰撞、末端空间和雅可比约束，当前优先解决时间、单位及命令/反馈一致性。

### 第二项：重复应同时区分策略循环与执行循环

- **策略循环**：实际命令轨迹重复，实测关节轨迹也重复，且相同本体阶段下视觉效果相近；可增强现有重复贡献。
- **执行循环/受阻**：命令持续变化，但本体反复停留或回到同一轨迹，视觉缺少进展；应由动作条件响应距离解释，不能因“命令不重复”就取消本体重复证据。
- **有进展的重复**：命令和本体相似，但物体视觉状态持续改变；降低无效重复惩罚。

分割实际单元时，夹爪目标先经过已验证的20 mm闭合映射，再与实测夹爪开合联合检查。不能把插值tick当作额外动作，也不能把新chunk尚未执行的尾段计入“已经重复了几次”。

### 第三项：保留LINe总体正常支持

LINe继续判断正常阶段分类器对当前特征是否有支持，不单独承担控制跟踪或任务成功判断。

### 怎样在动作发生前预警

chunk到达时，过期前缀长度、未来接续差异、预测关节包络已经可用；它们可以在新动作执行前提供计划层面的预警。对近期实际已执行单元建立模板，再用当前state与即将执行的短前缀预测是否回到无效循环。

尚未执行的chunk尾部可能会被下一次重规划丢弃，应按实际执行前缀长度设计预测时域。不能把未知未来视觉固定为当前视觉并当作“未来没有进展”，否则会系统性制造假重复。硬报警需要结合已经观察到的反馈与经过正常数据校准的预测置信度。

## 5. 本轮已经生效的重复权重

原始重复值乘常数后再重建经验分位数，排序基本不变，惩罚不会真正变强。V11在分位数变成尾部强度后提高相对权重：

```
c_j = -log10(p_j)
r = max(c_distance, 1.5*c_repetition, c_LINE)
```

三项卡片仍显示原始经验百分位，便于解释。1.5是在此次加权失败回放之前按用户要求固定的相对优先级；没有搜索失败起点标签。保持10帧均值、5帧确认，再用275条正常校准轨迹的峰值重新标定，最终仍按尾部秩p≤5%报警。新边界为4.709939。

| 轨迹 | V10首次报警 | V11首次报警 | V11首段长度 | V11首个≥0.5秒段起点 |
|---|---:|---:|---:|---:|
| EP0 | 10.17 s | 10.10 s | 889帧 | 10.10 s |
| EP1 | 19.37 s | 18.17 s | 17帧 | 18.17 s |
| EP2 | 7.80 s | 6.27 s | 6帧 | 7.67 s |
| EP3 | 8.77 s | 8.70 s | 292帧 | 8.70 s |

EP0的主要改善是报警更连续，首次时间只提前2帧。EP2的6.27秒首段只有0.2秒，不能称作从此持续介入。持续段字段只用于事后评估，不进入因果推理。

正常校准仍12/275条报警。正常验证从14/275降至12/275（4.36%），但报警帧从112增至140/314751：轨迹误报减少，已触发轨迹的报警持续时间有所增加。

原三条异常由2/3变为3/3出现报警，原EP0指定尾部也出现报警。不过首次触发多在约2.7–3.1秒，部分段只有几帧；不能据此宣称正确定位全部故障。新旧评测集均为历史回归集，没有故障起点真值，不是新的独立泛化验证。

这些正式报警变化来自重复权重调整；本轮的限幅、计划接续及响应图尚未贡献到硬报警。
